# ADR-0006：管线流程并发化

- **状态**：Accepted（进程池并发 + TransNet worker 并行均已落地；worker 的 CPU 争抢代价已量化）
- **影响文件**：`pipeline.mjs`（`buildPages` / `searchCandidates` / `runPool`）、`dsh-plugin/index.js`（返回 timings）
- **相关**：ADR-0005（TransNet 采样）、ADR-0004（动作采样）

## 背景

ADR-0005 把 TransNet 减半之后，管线的时间结构变了。一次 15 秒视频（开 ASR + OCR）的实测：

```
抽基础帧        0.85s
帧差检测        0.39s
TransNet       10.93s
ASR             6.83s
补帧            2.23s
分组+分页       7.33s
字幕提取（OCR）  8.93s
─────────────────────
                37.50s
```

不再是「一个模型吃掉六成」，而是七八个阶段各占一成到三成。**这时候再优化单个模型收益有限，要压缩的是「它们之间本来可以重叠、却排队等着」的时间。**

## 关键发现：两个隐藏大头

真正拖时间的不是模型，而是**串行 spawn 的子进程**：

1. **拼图**：`buildPages` 里每页一次 `execFileSync('montage')`。一页 0.5~1 秒，22 页就是十几秒。这段时间 Node 主线程**什么也没干**，只是在等进程结束。
2. **补帧**：每条 ASR 台词要取若干帧，原来每帧一次 `execFileSync('ffmpeg')`。台词密集时 60 帧 = 60 次串行 spawn。

两者都是**纯 IO/进程等待**，天然可并发。

## 采纳：进程池并发

```js
const MONTAGE_CONCURRENCY = Math.max(2, Math.min(6, cpus().length - 1))
function runAsync(cmd, argv) { ...spawn + Promise... }
async function runPool(jobs, limit) { ...N 个 worker 轮询取任务... }
```

- **拼图**：把所有页的 montage 命令先收集成 jobs，再交给 `runPool`。
- **补帧**：改成两阶段——同步阶段算清预算与采样点（不 spawn），异步阶段用同一个池并发提取。
- 并发度取 `min(6, CPU数-1)`：留一个核给主线程和其他 ffmpeg。

### 实测

| 项目 | 改前（串行） | 改后（并发） |
|---|---|---|
| 拼图分页（CONCAT 22 页） | 21.6s | — |
| 拼图分页（15s 片 13 页） | — | **4.96s** |
| 补帧（60 张） | 40s+（估算） | **9.9s** |
| 15s 片总耗时（开字幕） | 42.3s | **33.8s** |

**这段收益和模型优化无关，纯粹是把等待时间叠起来。**

## 顺带：分段计时进返回

`pipeline` 收集每阶段耗时写入 `index.json` 的 `timings`，`video_analyze` 原样返回。以前判断瓶颈要靠 bench 脚本猜，现在每次调用都自带。

## 后续实测：worker_threads 真并行（2026-11-05 补充，已采纳）

上文「暂不采纳」的判断被后续实测推翻了——**并行是赚的，只是赚得不多**。

### 做法

把 TransNet 挪到 worker 线程（`lib/transnet-worker.mjs`），主线程同时跑 ASR 与 OCR：

```
主线程：抽帧 → 帧差 → [启动 worker] → ASR → OCR → [取 worker 结果] → 补帧 → 分页
worker：                TransNet（解码 + ONNX 推理）
```

worker 起不来时自动退回主线程同步跑（`--serial` 也可强制串行，用于对照）。

### 三组交替对照（15 秒片，ASR 开、字幕关，交替 3 轮）

| 轮次 | 模式 | ASR | TransNet 墙钟 | 总耗时 |
|---|---|---|---|---|
| 1 | 串行 | 4.4s | 6.3s | 22.42s |
| 1 | **并行** | 6.4s | 0.7s | **18.35s** |
| 2 | 串行 | 4.9s | 7.8s | 25.31s |
| 2 | **并行** | 7.3s | 1.6s | **21.03s** |
| 3 | 串行 | 4.9s | 8.1s | 25.48s |
| 3 | **并行** | 6.6s | 2.3s | **21.06s** |

均值：**串行 24.4s → 并行 20.1s（1.21x）**，三轮全胜。

### 代价与收益拆解

- **TransNet 墙钟**：7.4s → 1.5s（省 5.9s，被 ASR 期间藏掉了）
- **ASR 自己变慢**：4.7s → 6.8s（**+2.1s**，两个 WASM 抢 CPU）
- **净收益 ≈ 3.8s**（与实测的 4.3s 吻合）

**并行不是免费的**：sherpa 与 onnxruntime 同时跑会互相拖慢。收益 = 被藏起来的时长 − 争抢损失。因为 TransNet（7.4s）明显长于 ASR（4.7s），所以藏得下、还有赚。

### 为什么之前那次测出「并行更慢」

早先有一轮并行总耗时 36.2s、ASR 14.3s，看着像亏。事后核对：那一轮抽基础帧从 0.9s 涨到 1.5s，**整机在热/有后台负载**。交替三轮的干净数据里没有复现。**单次样本不足以下结论，必须交替对照。**

### 边界

- 内存：整机 app RSS 417MB（含 worker 的 ORT 实例），没 OOM，但余量不大——**不要再往 worker 里塞第二个模型**（比如把 OCR 也搬进去）。
- 只验证了「TransNet vs ASR」这一对。**OCR（主线程，最长 19s）仍没有并行伙伴**，它才是字幕密集片的瓶颈。
- 结论依赖「TransNet 比 ASR 长」这个前提。如果换个更快的镜头检测模型，争论代价可能反超收益。

## 原判断（保留作对照）：worker_threads 真并行

`Promise.all` 包住 TransNet / ASR / OCR **没有用**——三个模型都在 Node 主线程里同步执行（ORT WASM、sherpa WASM、PP-OCR 全同步），包起来只是排队。

理论上的解是 `worker_threads`：TransNet 一个线程、ASR/OCR 另一个，真正叠起来。

**暂不采纳的理由**：

1. **内存**。sherpa 的 paraformer int8 模型 217MB，多开一个线程就多一份 WASM 实例与模型副本；PP-OCR 与 ORT 同理。手机上很容易撞到 OOM，而 OOM 是**整条管线崩掉**，比慢几秒严重得多。
2. **收益有上限**。当前阶段里最长的是 OCR 8.9s，TransNet 7.2s。即使完美并行，理论下限也是 `max(各段) ≈ 9s` 加上串行的抽帧/帧差/分页 —— 大约从 33.8s 压到 18~20s，**约 1.7x**。
3. **复杂度换来的东西不对等**。worker 里要重新处理模型加载、日志、错误传播、临时文件竞争；一旦某条 worker 崩了，现在的错误报告体系全要重做。

**结论**：先记在这，等实际使用中确认「OCR/TransNet 真的是痛点」再立项。

## 边界与未解

- **数据是单次样本**。这台机器上同一段视频，TransNet 从 7.2s 到 15.9s 都出现过（后台有其他进程时）。**相对提速可信，绝对值不可跨环境引用。**
- **补帧耗时与台词密度强相关**：30 秒的「臭肥鱼」只花 2.23s（两条长台词），15 秒的「捏脸」花 6.5s（五条短台词）。它不是固定开销。
- **并发度的合理性没校准**：6 是否最优？没测 2/4/8 的对照。手机上 CPU 大小核调度不透明，可能 4 更好。
- **OCR 仍串行且独立**：它和 TransNet、ASR 完全不依赖，是目前唯一「还没被并发吃掉」的大块（8.9s）。要用上它必须上 worker_threads，理由见上。
- **montage 本身可以更省**：现在每页都要重新解码所有帧图。如果改成一次性布局（ImageMagick 的 `-page` / 或改 ffmpeg xstack），可能连并发都不需要。没验证。
