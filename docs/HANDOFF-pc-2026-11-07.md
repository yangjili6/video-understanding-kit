## 一、最优并发路数（最高优先）

### 1.1 现在的规则

选档目标是：

```
N* = max { n | E_n ≥ 40% ∧ G_n ≥ 8% }
```

其中：

- `T_n`：n 路并发的耗时中位数（同一批输入、同一计时口径、多次测量）
- `E_n = (T_1 / T_n) / n`：并行效率
- `G_n = (T_{n-1} − T_n) / T_{n-1}`：边际收益

**两条阈值同时满足才往上加一档。**

### 1.2 手机端的实测结果

**52 帧、TransNet 固定串行、三档对照**：

| 配置 | wall 中位 | 效率 | 边际 | 判定 |
|---|---|---|---|---|
| 1 路 | 53.3s | — | — | 基准 |
| 3 路 | 25.5s | 69.7% | 52.2% | ✅ 通过 |
| 4 路 | 26.9s | 49.5% | **−5.5%** | ❌ 拒绝 |

**推荐 3 路。** 关键发现：4 路在**单轮**里确实更快（24.95s），但**中位更慢**、温度高 2~4℃，边际收益为负。

### 1.3 需要你在 PC 上回答

```bash
node tools/calibrate.mjs <视频> --max 16 --frames 48
REPS=5 node tools/calibrate.mjs <视频>        # 每档 5 次
COOLDOWN_MS=0 node tools/calibrate.mjs <视频> # 不冷却，模拟连续使用
```

**问题**：

1. **曲线形状**：PC 上 1→16 路的加速曲线是什么样？拐点在第几路？
2. **阈值适配**：40% / 8% 这两个数对 PC 合适吗？
   - 手机 4 个大核就被打满，效率掉得快
   - **桌面核多、无功耗墙，可能 8 路都还在线性区** —— 那这套规则会推荐一个很高的值
3. **温度影响**：PC 上连续跑会不会也热到降频？如果不会，那手机端的温度保护在 PC 上是多余的吗？
4. **上限该定多少**：如果公式一路推到 32 路，实际有意义吗（内存、调度开销）？

### 1.4 手机端踩过的坑（省你时间）

| 坑 | 说明 |
|---|---|
| `os.cpus()` 在 Android 返回空数组 | `lib/cpu.mjs` 改读 `/sys/.../cpu_capacity`；**PC 上走 `os.cpus()` 分支，不受影响** |
| 冷机/热机差 40% | 同配置测出过 45.3s / 63.4s；**别用单次测量选档** |
| worker 内部线程数 | 已确认全是 1（`ort.env.wasm.numThreads = 1`），不存在多层并行互抢 |
| 4 路效率低的原因 | 不是线程超订，是 4 个大核本身的调度与功耗墙 |

## 二、光流方向（时间够再看）

### 2.1 背景：为什么想起光流

手机端看视频是**一页页读网格图**，不是人类那种连续观看。想改进成「**漫画式分镜**」：

```
去重（相似帧合并）+ 时间流（按顺序排）→ 每格都有意义，没有废格
```

**判定「哪些帧值得留」需要看运动**，而像素差会被光照/压缩噪声干扰，**光流看的是「东西有没有动」**。

### 2.2 但 ADR-0003 曾经否决过光流

**它否决的是「用运动强度调抽帧率」**：

```
实测低运动占比仅 2.2%（两部动画片）→ 自适应抽帧省不了多少 → Rejected
```

**关键**：

- 旧用途：拿运动强度决定「少抽多少帧」—— **动画片几乎全程在动，省不了**
- 新用途：拿光流决定「哪些帧值得看」—— **动画片全程在动反而是好事**
- ADR-0003 自己写了边界：**结论只对这两部动画成立，真人/监控可能反转**

**所以光流没被真正否决，只是没换用途重新评估。**

### 2.3 需要你在 PC 上做的事

**如果时间够**，做个小实验：

1. **光流当判断器**：ffmpeg 的 `opticalflow` 滤镜输出向量场，别可视化，直接算统计量：

   ```
   平均位移量（去掉全局位移后）→ 是不是「有动作」
   光流的空间一致性 → 是镜头移动还是物体运动
   ```

2. **验证去重效果**：拿一段动作片（比如羽毛球），对比两种去重策略保留下来的帧：

   ```
   A. 按像素差去重
   B. 按光流去重
   看 B 是不是保住了 A 丢掉的「细微但重要」的动作帧
   ```

3. **成本核算**：光流在 PC 上跑一段 30s 的视频要多久？值不值得进管线？

## 三、交接注意事项

### 3.1 两个仓库概念

| 目录 | 角色 |
|---|---|
| `video-understanding-kit` | 源码仓库（有 remote，push main + release） |
| `dsh-plugin/lib/videokit/` | 由 `scripts/sync-videokit.mjs` 生成的副本，**不要手改** |

新增模块要加进 `sync-videokit.mjs` 的 `FILES` 清单，否则 `sync` 不认。

### 3.2 版本策略

**开发期不刷版本号**，统一保持当前值，**等真正发 release 时才升**。

### 3.3 ADR 配图规范

- 结构图：写 SVG 生成脚本 → 存 `docs/diagrams/*.svg`
- 公式：用 CodeCogs 渲染 → 转黑底白字 PNG（`magick` 两步：先 flatten 白底，再 negate）
- **正文引用 PNG 而非 SVG**（GitHub 只给位图 lightbox，SVG 不能点开放大）

### 3.4 产物清理

`video_analyze` 每次会留几百张网格图，已加自动清理（保留最近 5 个目录，`DSH_VIDEO_KEEP_OUT` 可调）。PC 上如果输出目录也在同一路径结构下，逻辑通用。
