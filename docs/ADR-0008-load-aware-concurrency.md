# ADR-0008：按 CPU 负载决定并行度

- **状态**：Proposed（2026-11-05，机制已落地，收益不稳定，需要更多样本）
- **影响文件**：`lib/cpu.mjs`（新增）、`pipeline.mjs`、`subs.mjs`
- **相关**：ADR-0006（TransNet worker）、ADR-0007（OCR 分片并行）

## 背景

ADR-0006 和 ADR-0007 各自都测出了「并行有效」（1.21x 和 1.42x），但**把它们同时打开后测出了相反的结论**：

| TransNet | OCR 路数 | 总耗时 |
|---|---|---|
| 串行 | 1 | 71.21s |
| worker | 1 | 94.68s |
| 串行 | 3 | 90.13s |
| worker | 3 | 114.5s |

而且更糟的是一致性：**同一个配置（OCR 2 路 + TransNet 串行）连续跑两次，总耗时 64.49s 和 135.57s**——相差一倍。

结论只能是：**手机的算力状态本身在剧烈变化，配置不是决定因素。** 于是需要先能「感知状态」，才谈得上选配置。

## 探测：Android 上能读什么、读不到什么

| 信号 | 结果 |
|---|---|
| `/proc/loadavg` | 读不到（空） |
| `/proc/stat` | **EACCES 权限拒绝** |
| `thermal_zone*/temp` | 读不到 |
| `os.cpus()` | **返回空数组**（length=0） |
| `/sys/.../cpu_capacity` | ✅ 可读 |
| `/sys/.../cpufreq/scaling_cur_freq` | ✅ 可读 |

**唯一可用的实时信号是 cpufreq 的当前频率。**

### 顺带测出的 CPU 拓扑

```
cpu0-3   capacity ≈ 494~509   2.4GHz   ← 能效核
cpu4-6   capacity ≈ 873       3.3GHz   ← 性能核
cpu7     capacity = 1024      3.63GHz  ← 超大核
```

**1+3+4 结构**。所以「8 核」里能跑满的只有 4 个——之前 `cpus().length || 4` 的兜底刚好接近，但那是运气。

## 策略

```
大核频率比 ≥ 65%  → cool   → 全并发（计算型 max 4，IO 型 max 8）
45% ~ 65%        → warm   → 计算型最多 2 路
< 45%            → hot    → 计算型退回单路（串行）
读不到频率        → unknown → 不据此调整
```

**计算型（WASM 推理）按大核数**，**IO 型（montage/ffmpeg 子进程）按总核数**——子进程不占主线程的 WASM 池，可以用小核。

### 一个必须记住的时序坑

第一版把负载探测写成模块级常量：

```js
const DETECTED_LOAD = detectLoad(CPU_TOPOLOGY)   // ❌ 模块加载时执行
```

结果永远测出 `cool`——**因为那一刻流水线还没开始跑，CPU 正闲着**。负载必须在「做决定的这一刻」测（TransNet 启动前、OCR 开始前）。

这条和 ADR-0006/0007 的两个坑是一类问题：**代码能跑、不报错，只是判断依据是错的**。

## 实测：机制生效，但耗时仍然不可预测

同一台设备、同一段片子（26s，10 条字幕），负载判为 hot 后：

| 轮 | 负载判定 | OCR 路数 | det | 总耗时 |
|---|---|---|---|---|
| 1 | hot（22%） | 2 | 24.37s | 56.7s |
| 2 | hot（21%） | 2 | 27.88s | 64.49s |
| 3 | hot（31%） | 2 | 90.96s | **135.57s** |

**前两轮 56~64 秒，第三轮 136 秒。** 配置完全相同。

## 边界与未解

- **频率比区分不了「空闲」和「降频」**：CPU 闲着时频率也是低的（实测冷却后也只到 50~58%）。所以 hot 判定可能把空闲误判成过热，白白退回串行。
- **采样点太稀疏**：一次运行里只在两个时刻采样（TransNet 前、OCR 前），中途升温感知不到。
- **为什么第 3 轮会 136 秒没有解释**：可能是其他进程、可能是持续高温、也可能是测量假象。**在没有解释之前，不能承诺任何固定提速比例。**
- **没做交叉验证**：同一负载档位下「串行 vs 并行」的对照还没跑（这次的 hot 判断只对 TransNet 生效，OCR 仍走了 2 路，变量没隔离开）。
- **兜底并发度 4 是猜的**：`cpus().length || 4` 刚好和这台机器的大核数吻合，但别的机型不一定。

## 结论

**机制保留，默认保守**：热时串行、冷时并行，且允许 `SUBS_DET_WORKERS` / `--serial` 手动覆盖。

**不写进发布说明的性能数字**——因为它不稳定。这一条写进文档本身就是结论：**在这个设备上，「并行一定更快」是错的假设。**
